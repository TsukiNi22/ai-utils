# claude-cluster

Run and drive several Claude Code sessions in parallel, one or more per project, from one terminal or one window.
A **global session** manages the others (spawn, prompts, permissions, modes, tasks) through its own MCP server, by
text or by voice. Claude Code is the default agent; Ollama (local), Anthropic-compatible endpoints, OpenAI-compatible
ones (Qwen Code), opencode and the OpenAI Codex CLI work too.

## Installation

Built and installed by the `setup.sh` of the repository, like `xstyle` (binary in `~/.local/bin`, bash / zsh / fish
completion):

```bash
./setup.sh install claude-cluster          # from a clone of ai-utils
curl -fsSL https://raw.githubusercontent.com/TsukiNi22/ai-utils/main/setup.sh | bash -s -- install claude-cluster
./setup.sh remove claude-cluster
```

The completion is generated by `claude-cluster --completion bash|zsh|fish` and installed like the one of `xstyle`:

| Shell | File | Loaded |
|---|---|---|
| bash | `~/.local/share/bash-completion/completions/claude-cluster` | on demand by bash-completion, open shells included |
| zsh | `~/.local/share/zsh/site-functions/_claude-cluster` + the `# >>> tsukini-skills completion >>>` block of `~/.zshrc` | new shells; the command for the current one is printed |
| fish | `~/.config/fish/completions/claude-cluster.fish` (if fish is installed) | on demand, open shells included |

It completes the commands and flags with their description (zsh, fish), and the values: session names and the trash
of the running instance, tasks, providers, backends (`claude/opus`, the local Ollama models as `ollama/<model>` and
`ollama-openai/<model>`, the opencode models), profiles, styles, permission modes, layouts, folders
(`claude-cluster __complete <kind>` gives them as `value<TAB>description`).

By hand: `cmake -S ai/claude-cluster -B build -DCMAKE_BUILD_TYPE=Optimized && cmake --build build --parallel && cmake --install build --prefix ~/.local`.

## Usage

```bash
claude-cluster                          # terminal interface when in a terminal, else a window
claude-cluster --gui                    # window (fails when Qt6 is not built in or there is no display)
claude-cluster -g --tty-mode            # the window showing the terminal interface ([ui] gui_mode = tty keeps it)
claude-cluster --tty --layout grid      # terminal, sessions in a grid (list | grid; `tabs` is for the window / web page, the terminal shows the list)
claude-cluster --backend ollama/qwen3-coder   # backend of the new sessions for this run
claude-cluster --restore | --fresh      # previous run: restore / start new (default: asked, Esc = restore)
claude-cluster --rescan                 # ask at start to sync the map of this computer (even recent or refused)
claude-cluster serve                    # no interface: driven by the commands below and the MCP server
```

### Prompt

Like Claude Code: **`@`** completes the files and folders of the project of the session (the global session, whose
folder is its own: of the folder claude-cluster was started in, inserted as `~/...` paths), **`/`** the local commands,
the skills and the commands of the agent, then their arguments (`/cd` and `/new` folders, `/mode` modes, `/restore`
closed sessions). In the list: **Tab** completes without validating (into a folder: its content), **Enter** accepts
and closes, **↑ ↓** choose, **Space** / **Esc** close it (`\ ` + Space: a space inside a name).

**Modes of the prompt** (the terminal, the window, the web page; its sign and its target show it: `$ shell in <folder>`, `: command`):

| Prompt | What it does |
|---|---|
| `!<command>` | run by your shell (`$SHELL -c`) in the folder of the session, like `!` in Claude Code: the command and its output go in the conversation; given to the agent with your next prompt (not shown in it)? asked after it ran: **this time**, **always**, **not this time**, **never** (the palette, a list in the web page, `:share yes/no/always/never`); always / never are written in `[ui] shell_context = ask / always / never` (Settings > Interface: asked again); no session: its output is told. The web page and the app: refused unless `[web] shell = true`. Completion: the commands of your real shell (its aliases, functions, builtins, programs: read once from `zsh -i` / `bash -i`), then files; a command that lasts more than 8 s goes **to the background** (a shell `b1`: `/shells` lists them with their last lines, `/kill <id|all>` stops one and everything it started, its output comes in the conversation when it ends, a notice tells it); a **program that needs a terminal** (vim, nano, less, man, top, htop, ssh, a REPL, an interactive container...) is never run without one: the terminal interface hands it its terminal and takes it back when it quits (exit code told), the window opens a terminal emulator in the folder, the page says to use a terminal; Ctrl+K *Background shells* |
| `:s/old/new/[g][i]` | your last prompt of the conversation changed (a regex, any delimiter, `:%s` = every match), back in the prompt to send |
| `:r <file>` / `:r !<command>` | the file / the output of the command in the prompt |
| `:w [file]` · `:e <folder>` · `:q` · `:qa` | export the conversation (Markdown) · the session in another folder · close the session · quit claude-cluster |
| `:set <key>=<value>` | a setting (`ui.notify=false`, `layout=grid`; completed with their current value) |
| `:g/<text>/` | search the conversation |
| `:new` `:model` `:mode` `:effort` `:clear`... | the `/command` of the same name; `:help`: the list |

**Matching of the lists** (`[ui] matching`, Settings > Interface): the completions (`/`, `@`, `!`, `:`, `:set`, the
models, modes, efforts, the trash), the paths and the palette use **c2dmp-hsm** of libutils (`c2dmp`, the default): a
typo, a missing, doubled or swapped letter still finds it (`/modle` → model, `@redme` → README.md, `!gti` → git),
the closest first; the palette matches each word typed against the words of its actions (`mode:` / `share:`... keep
their kind). `raw`: what starts with the text typed, then what contains it.

**The terminal stays in the foreground**: Ctrl+Z never sends it to the background (in the prompt: undo; at a question of
the start: quit, asked again next time) and a stop signal is ignored; started with `&` it is refused (in `auto`, the
window opens instead when there is a display). In the background: `claude-cluster --gui &` or `claude-cluster serve &`.

| Key | Action |
|---|---|
| Enter | send (a local `/command` runs in claude-cluster, any other `/command` goes to the agent); while a turn runs the prompt is **queued** (shown under the transcript); the prompt leaves at once ("sent", "/clear…"): the send and the commands run in the background in their order, an error puts the prompt back |
| Alt+Enter / Shift+Enter | new line (prompt on several lines) |
| Esc | the last queued prompt of the session back in the prompt, removed from the queue (to edit it; one already given to claude stays) |
| Ctrl+↑ / Ctrl+↓ (or the wheel over them) | the side panels scrolled when they overflow (`▲ n above`, `▼ n more`) |
| F8 / `/now` / a click on the first queued line | the next queued prompt sent now: the running turn interrupted (the window: the palette; the web page: *Send the next now*; the control: `send_next`) |
| | **Queued prompts** of a Claude Code session are given to claude 1.5 s after they are typed (Esc edits them before): claude takes them at its next step, between two tool calls, like its own queue - not after the whole turn (`[sessions] queue_given = step`; `end`: held until the end of the turn, as before); shown `↳ given` meanwhile |
| Esc / Ctrl+C with voice prompts waiting | drop the last one / all of them (before anything else these keys do) |
| Esc Esc | clear the prompt; on an empty prompt (like Claude Code): the last turn leaves the conversation (claude goes on from the message before it, `--resume-session-at`) and its prompt comes back to be edited (again: the one before) |
| ↑ / ↓ | a line of the prompt; on its first / last line (or empty): the history of the prompts of the session shown, never looped; the prompt being written and the entries changed are kept while browsing (forgotten when a prompt is sent); every way to empty the prompt (send, Esc Esc, Ctrl+C, stash...) starts the browsing again from the newest |
| Ctrl+E | edit the prompt in an editor: `[ui] editor`, else the first installed of nvim, vim, vi, `$VISUAL`, `$EDITOR`, emacs -nw, nano (window: a multi-line dialog); the pasted texts are there in full, the ones left unchanged are blocks again after |
| Ctrl+Z / Ctrl+Y | undo / redo |
| Ctrl+A, Shift+← →, Ctrl+Shift+← →, Shift+Home / End | select all, by character, by word |
| Ctrl+← → , Home / End | move by word, to the start / end |
| Ctrl+X / Ctrl+C / Ctrl+V | cut / copy (with a selection) / paste: text, or an **image** of the clipboard as `[Image #N]` |
| Backspace / Delete / ← → on `[Image #N]`, `[Pasted text #N]` | the whole block at once (one character for the editor, like Claude Code) |
| Ctrl+S / Ctrl+P | stash the prompt / take the last one back (kept over the runs) |
| Ctrl+R | history of the prompts sent to the session shown (type to filter, Enter puts it in the prompt; Tab: every session) |

Local commands: `/pwd` (where the session runs: its folder, the computer, its pid - shown only, nothing sent), `/cd <folder>`, `/new <folder> [backend]`, `/mode <mode>`, `/rename <name>`, `/close`, `/interrupt`,
`/export [file]`, `/restore [session]`, `/clear` (a new conversation: the transcript emptied, archived in `logs/archive/` for `search`), `/model <name>` (same
conversation, another model), `/cost`, `/context`, `/rewind` (= Esc Esc on an empty prompt), `/exit` (= `/close`),
`/settings`, `/vim`, `/help`; the header of the session in focus shows how it runs: its provider / model, **api** (an API key, billed per
token) | **auth** (a login, a subscription) | **local**, its thinking (`think high`) and its mode (terminal, window, web page, app); the commands that only show something are answered here, in a popup, never asked to the
agent (nothing in its conversation, nothing spent): `/usage` (the 5 h / 7 d windows of the account, today, 7 days, this
session), `/info` (= `/status`, and Ctrl+K *Session info*: everything about the session in focus - agent, model, thinking, api / login, mode, folder, conversation, tokens, context, cost, the limits and the budget, the account windows), `/skills` (the skills of the user and of the
project, the plugins of Claude Code), `/mcp`, `/plugins` (the browser below); the commands of the agent (`/compact`,
skills...) are completed too. `::` completes the sessions (open ones with their state and folder, then the closed
ones) to point at one in a prompt (`ask ::backend to run its tests`; the agents are told what `::name` means). In the
prompt, a `/command` at its start, the `@files` and the `::sessions` are drawn in the accent colour on the surface,
like the pasted images and texts. A pasted image goes to Claude as an image block (to the
other agents as `@path`). The images are saved by content (`img-<hash>.png`): the same image pasted again (or its chip
clicked) is one more reference to the same `[Image #N]` ("here, here and here"), the image itself is sent once; the
images are numbered in the order of the text when sent.

**The Tasks session** (`☰ Tasks`, first in the list; `/tasks`, the palette *Tasks*, the window's *Tasks*
button - in the grid: a window of its own; next / previous session and Ctrl+B + an arrow go through it, before the
global session): what the sessions do and what waits, in place of a conversation. It has no prompt (its rows are
clicked, the palette, the global session or `claude-cluster task add` / `schedule add` make new ones).
- **Todo lists**: the list of each session (like claude.ai: ☒ done, ◼ in progress, ☐ to do; its TodoWrite /
  TaskCreate / TaskUpdate - `claude -p` gets its todo tools: `CLAUDE_CODE_ENABLE_TODO_TOOLS`); a session's own: its
  right panel *tasks*.
- **Task queue**: running, waiting, done, failed, cancelled (the first ones, `… +n more`), who made each (you, the
  global session, a session), where it goes, since when, why it was cancelled.
- **Scheduled**: the reminders and prompts at a time (`schedule_add`), waiting by their time, then the ones run (kept,
  counted) or cancelled.
- **A click on one: its actions** - start now (past the limit of parallel sessions) / run now, cancel or delete
  (a reason asked: told to the session that made it), archive (the archive: *▸ N archived*), open its session.
- **Without the mouse**: ↑↓ / `j` `k` choose a row (lit `▌`, kept in sight), PgUp / PgDn, Home / End (`g` / `G`),
  Tab / Shift+Tab the next / previous part, Enter / → / Space its actions (a todo list: its session); the window:
  ↑↓ / Tab between its links, Enter; the web page: Tab or ↑↓ / `j` `k` between its rows, Enter / Space. With no
  session yet, the Tasks session is still shown (its queue, its schedules).
- A session closed: its waiting tasks and schedules cancelled ("its session was closed"); deleted for good: removed.
- The control: `task_act` / `schedule_act` (cancel, delete, archive, unarchive, force / trigger, a reason), `todos`;
  the MCP: `task_act` (the global session).

**Sessions by hand**:
- **A new session on a project**: `/new <name>`, `/cd <name>`, the palette *New session on a project*, the web page,
  `claude-cluster spawn <name>` and the global session (`session_spawn`) take a folder or the name of a project of the
  map of this computer (its git repositories, `machine.md`): the closest by its name (a typo found: c2dmp-hsm), its
  path / kind / origin far behind. The folders are completed with the projects first (`/cd alph` → alpha-engine).
- **A right click on a session** (the list; a long press in the web page): its menu - open, rename,
  describe, move to another folder, open its folder / a terminal there, **archive** (closed, to the trash, restorable)
  and **delete for good** (asked first: yes / no; its conversation gone, not in the trash).
- **In the session**: `/close` (archived), `/delete` (asked first), `/delete!` (at once, no question). The global
  session: `session_close`, then `session_purge` for good (only when you asked).

**Chips** above the prompt, one per image / pasted text of the prompt (dim when removed from the text): mouse over shows
the image (terminal: its pixels as half blocks through `magick`, or the symbols of `chafa` with `[ui] image_preview =
"chafa"`; window: the image itself) or
the pasted text; **click** puts it back in the prompt; **right click** opens the image in the viewer of the desktop
(`[ui] image_viewer`, default `xdg-open`: the real image, outside of the terminal).

**History and stash** keep the images and the pasted texts of a prompt: one taken back (↑, Ctrl+R, Ctrl+P) has its
`[Image #N]` and its `[Pasted text #N]` blocks again.

**Pasted text**: a paste of more than `[ui] paste_lines` lines (3) or `paste_chars` characters (800) is one
`[Pasted text #N +L lines]` block in the prompt (0: never); it is sent, stashed, edited (Ctrl+E) as its full text. In
the terminal the paste of the terminal itself (Ctrl+Shift+V, bracketed paste) arrives in one piece: its new lines don't
send the prompt.

**Vim mode** (`/vim`, the palette, or `[ui] vim = true`): the prompt starts in Insert (`-- INSERT --`), **Esc** goes to
Normal (block cursor, `-- NORMAL --`): `h j k l` / arrows, `w b e`, `0 ^ $`, `gg G`, `f t F T<c>`, `x X s S D C`,
`dd cc yy`, `d c y` + a motion, `p P`, `u` / `Ctrl+R`, `~`, `J`, `r<c>`, counts (`3w`, `2dd`), `v` / `V` visual
(`d x c y ~`), `i a I A o O` back to Insert. In Normal: **Enter** sends, **Esc** with nothing pending does the Esc of the
prompt (queued prompt back, Esc Esc clears), the Ctrl / Alt / F keys stay the shortcuts.

**Transcript** like Claude Code: `⏺` the answers and the tool calls (`Bash(ls)`, `Update Todos` with its ☐ ◼ ☒ list),
`⎿` the first 3 lines of a result (`… +N lines`), `∴ Thinking` folded, the live thinking, and a state line while a turn
runs (`✻ Running Bash… (12s · ↓ 1.2k tokens · Ctrl+C to interrupt)`); **Ctrl+O** unfolds the thinking and the results.
Blank lines between the blocks (prompt, thinking, tool, answer; a result stays with its tool). The **Tokens** panel
tells the new tokens apart from the ones read again from the cache at every step of a turn (`3k +118k cache`: each
tool call reads the whole context again, cheap from the cache). The answers are **typed as they come** (`[ui] typewriter`, `typewriter_speed` characters / s): the agents often send
their tokens in bursts, the text still appears a few characters at a time (faster by itself when a long text is
behind, never more than ~1.5 s late), only what comes while a session is shown: switching to a session shows what it
has at once; `typewriter = false`: shown as received.

Panels of a session (each one enabled per session from the palette): **tokens** (last prompt, current one, total),
**context** (used / window), **cost** (session, last turn, budget, 5 h / 7 d limits), **usage** (the vendor of the
session: tokens and cost today, the last 7 days, lifetime, with the breakdown the API gives - input, cache written (5
min / 1 h), cache read, output, thinking; the windows of the account; the budget left), **skills** (loaded,
available), **git** (branch, graph of the commits), **diff** (`git diff --stat` + diff), **tools** (timeline),
**files** (modified).

The numbers of **tokens** are the API's own (the `usage` of each answer: input, cache written 5 min / 1 h, cache read,
output and its thinking part), shown per turn and per session with their breakdown. The **usage** of Anthropic is
read from the transcripts of Claude Code (`~/.claude/projects`, `[usage] transcripts`, or `CLAUDE_CLUSTER_TRANSCRIPTS` in
the environment of the core - folders apart by `:`, empty: none): every session of this
computer, in claude-cluster or not, summed by day and model as the files grow (a message streamed is counted once).
Its **cost** uses the price of each model: `[usage.prices]` in `config.toml` (`"claude-opus-5-5" = 15` $ per million
input tokens, the output 5x, the cache written 1.25x / 2x, read 0.1x; or `[input, output]`), else the price **learned**
from the cost Claude Code tells for its own turns (`prices.json`, exact for its table), else the public table of the
known models; unknown: the cost says so. The **windows of the account** (5 h, 7 d, a model's 7 d, the extra usage
credits) come from the usage endpoint of claude.ai with the token of Claude Code (`~/.claude/.credentials.json`, sent
to that endpoint only, never shown or logged), read every 5 minutes, after a turn and when the usage is asked
(`[usage] account = false` keeps the ones the last turn told). The other vendors (codex, ollama...) keep the ledger of
claude-cluster (`usage.jsonl`, with the same breakdown from now on). `claude-cluster usage [vendor]` and the `usage`
tool give all of it as JSON (the breakdown, the windows, the source).

Model and thinking effort of a session (the same conversation goes on, the session started again): the palette
(*Model: ...* - the Claude aliases and ids, `ollama list`, `opencode models`, the `[models]` of the config - and
*Effort (thinking): ...*), `/model [id]` and `/effort [level]` (completed), `claude-cluster model / effort`, or the
global session (`session_set_model`). Effort: claude `--effort` (low, medium, high, xhigh, max), codex
`model_reasoning_effort`, opencode `--variant`; the default of new sessions is `[agent] effort`.

## Backends

`--backend` / `spawn --backend` / `[agent] provider` take `<provider>[/<model>]`. `[agent] provider` (settings page > Agent >
*Provider of every session*, applied at the next start) is the one of the global session, of every sub-session - the
existing ones too, moved to it at the start - and of the conversations opened with `session_import` / `external`; the
sessions of another driver (codex, opencode, qwen) keep their own. It replaces `[agent] default` and `[global] backend`,
still read when `provider` is missing:

| Provider | Driver | What | Credentials |
|---|---|---|---|
| `claude` = `anthropic` | claude | Claude Code, its own login (default) | `claude-cluster auth login anthropic` (= `claude auth login`) |
| `anthropic-api` | claude | Claude Code with an API key | key stored by `auth login` |
| `ollama` | claude | Claude Code on a local Ollama model (Anthropic API of Ollama) | none (`ollama serve`, `ollama pull <model>`) |
| `openrouter`, `deepseek`, `kimi`, `zai`, `minimax` | claude | Claude Code on an Anthropic-compatible endpoint | key |
| `openai` | qwen | Qwen Code on the OpenAI API | key |
| `ollama-openai` | qwen | Qwen Code on a local Ollama model (OpenAI API) | none |
| `opencode` | opencode | opencode and its providers (`opencode/<provider>/<model>`) | `opencode auth login` |
| `codex` | codex | OpenAI Codex CLI | `codex login` |
| own `[providers.<name>]` | claude / qwen | any Anthropic- or OpenAI-compatible endpoint (LM Studio, vLLM...) | optional key |
| `groq`, `deepgram`, `elevenlabs`, `cartesia` | voice | the engines of the voice (see [Voice](#voice)), not agent backends | key |

```bash
claude-cluster auth list                 # every provider: ready or not, and why
claude-cluster auth login openrouter     # API key asked without echo, stored in the keyring (secret-tool) or credentials.json (0600)
claude-cluster auth logout openrouter    # key removed (login providers: their own logout)
```

**Settings > Accounts & limits** (terminal, window, web page): every provider with its state (key stored / login done /
not ready and why) - Enter on a key provider asks its API key (without echo; the keyring, else `credentials.json`
0600; never `config.toml`), the row under it removes it; a login provider runs its own login. The **limits** are what
the sessions may spend *together* (the USD of the usage ledger): per day (since the local midnight), per week (the last
7 days), per month (since the 1st), each with its spending shown, **Counted** (`keys`: only what an API key is billed
for - a subscription costs nothing more per turn - or `all`), **Block at the limit** (the prompts refused, `send
--force` passes; or only warned) and **Warn at** a share of a limit (a notice and a notification, once per window).
`[limits]` and `[sessions] budget_usd` are protected: the global session never changes them.

> [!IMPORTANT]
> The **claude** driver is the complete one: one process per session, live permissions in the interface, the MCP
> server, Remote Control. The other drivers start one process per turn (the conversation is resumed with its id):
> their permissions follow the mode (`plan` read-only ... `bypassPermissions`), they can't be asked live.

> [!NOTE]
> Permission modes: the new sessions start in **`auto`** (`[agent] permission_mode`, the classifier of Claude Code
> allows the safe actions, like an interactive Claude Code); `[global] permission_mode` sets the one of the global
> session (default `bypassPermissions`: it never asks, applied at every start). The claude sessions are launched with `--allow-dangerously-skip-permissions` (`[agent] allow_bypass`):
> without it Claude Code refuses to switch to `bypassPermissions` later. The mode shown is the one Claude Code
> confirms; a refused change is shown as an error.

> [!WARNING]
> The cost shown for a non-Anthropic provider through Claude Code is a guess of claude (Claude prices): it is shown as
> `local / unknown`. A small local model may not follow the tools of Claude Code well (7B+ coder models recommended).

## Global session

A session of its own (`[global]`: folder, model; its provider is `[agent] provider`, a claude-driver one) with:
- its **system prompt** `~/.config/claude-cluster/global.md` (written once, customizable: settings page > Global session >
  *System prompt (edit)* opens it in the editor - `[ui] editor`, else nvim, vim, vi... - and starts the session again on
  the same conversation), added to the global `CLAUDE.md` (an empty file: none);
  it ends with a compact **toolbox** (`templates/global.md`: the MCP tools by family and when to use each - sessions,
  callbacks `[reply from ...]`, tasks and schedules, displays, settings - what not to do); the one of the sub-sessions
  (`templates/sessions.md`, `~/.config/claude-cluster/sessions.md`) tells how their answers are shown, the callback to the
  global session (compact answers), AskUserQuestion, the cluster commands and what never to do; the long details stay in
  `cluster_info` and this README (both files are copies written once, never refreshed: `config_files` shows them);
- the **map of this computer** `~/.config/claude-cluster/machine.md`: you (nickname, email, main editor, language of the
  answers, notes: `[user]` of the config, asked at every sync with their current value ready - Enter keeps it - or a
  suggestion: git identity, editors installed, `$LANG`),
  the OS and the hardware (CPU, memory, GPU, disks), the tools and their versions, the shell (aliases: the dangerous
  ones - locking the session, deleting files, powering off... - and the ones replacing a common command, with the
  `\cmd` form to use; functions, PATH, names of the variables), packages, git / GitHub identity, Claude Code config
  (skills, plugins, MCP servers), docker / podman images and containers, folders, language, keyboard, time zone, SSH
  hosts, and the git repositories of the home folder (5 levels, hidden folders skipped: path, kind, branch, origin,
  last activity). Asked at the first start (no: not asked again) and proposed again when older than
  `[ui] machine_days` (30), each time with what is read and stored, y / n; synced from the settings page, the palette
  or `claude-cluster machine sync` (`--rescan` at start: its question forced), its progress in a box in the middle of
  the screen (over any page, Esc hides it) (~5 s: the slow commands run in
  parallel). Local only; the global session reads it for a request about a local project, the user or the system;
- the answer of a sub-session it asked (`session_send`) **comes back to it** as a message `[reply from <name> (<id>)]`
  when the sub-session is done: no polling of `session_read` (each read costs a whole context);
  the text goes in `text` (`prompt` / `message` / `content` are taken too); a send with no text is refused, never sent as an
  empty `[from the global session]` prompt (`tests/send_prompt.sh` checks it with a fake `claude`);
  every end of a turn started for the global session calls it back **once**: the answer to the first prompt of a
  `session_spawn` (`reply: false` opts out), a later turn the agent starts by itself when a background task / Monitor
  completes (`[reply from ...]` with a note), an API error (`[error from ...]`, weekly limit...), an interrupted turn
  (`[interrupted: ...]`), an agent that exited; a task queued by the global session (`task_add`) is answered the same way
  (`tests/callbacks.sh` checks it with a fake `claude`);
- **one-shot sessions**: `session_spawn` `one_shot: true` (set by the global session for ONE precise task, never for a project it
  will talk to again) closes the session to the trash (restorable) once its answer was relayed, when *Archive one-shot sessions*
  (`[sessions] archive_one_shot`, on by default) allows it - the flag is ignored when it is off. It stays when the user typed
  in it, shows it right now, it waits for a permission / question, another prompt is queued, or its turn failed / was interrupted;
- the task queue: a task whose target session does not exist (closed, never created) or whose dependency failed fails
  with its reason (`error` in `task_list`, told to the session that queued it); the finished tasks are archived after
  30 minutes (`task_list` `archived: true` lists them too; the Tasks session shows them under "archived");
- **notifications** (`[ui] notify`, `notify_global` / `notify_done` / `notify_permission` / `notify_sound`, `notify_app` for the Android app): the end of
  its answers, of the turns of the sub-sessions, a permission waiting; failsafe (no `notify-send`: nothing). See
  [The icon and the notifications](#the-icon-and-the-notifications);
- `/clear` and a new start (`n` at start) only start the context of claude again: the transcript stays, marked
  "new conversation" (the sub-sessions go to the trash as before);
- **several projects at once**: a request touching several projects is split, a task per project, sent as a group
  (`session_fanout`): their sessions (or their folders: created; a pattern `match` {under, has, name}: past 10 projects
  or sessions to create, the list is shown to the user first), a chain (`after`: a task gets the answer it builds on),
  a wait the global session chooses (`all`, `first`, `count`, `timeout_minutes` with what came, `stop_others`), a failed
  task tried once more; the global session is woken **once** with their answers and merges them (or a session of its
  own for a big merge: `merge: session`; `table`: a comparison table too); its progress card in the transcript of the
  global session, a notification at its end. The tasks go through the task queue: **parallel sessions**
  (`[sessions] max_parallel`: sub-sessions working at once) past which they wait in the **task queue** (`task_queue`:
  how many may wait, a new one past it refused), sent as soon as a place is free;
- **Start over** (the palette, Ctrl+K): every sub-session to the trash (restorable), the queued tasks and groups
  stopped, a new conversation for the global session - after a yes / no;
- it **stays**: its process ending by itself (not a stop) starts it again on its conversation (once a minute at most,
  told in the status line);
- between sessions, few tokens (like `rtk`): the results of the MCP tools are compact JSON without their empty fields,
  the answers of a sub-session to the global session (`[from the global session]`, a task of a group, `[questions from ...]`)
  terse `key: value` lines with quiet commands, the prompts of the global session the task only; what the user reads stays normal;
- the **MCP server** `claude-cluster mcp`: `session_list`, `session_status`, `session_spawn`, `session_send`,
  `session_allow`, `session_set_mode`, `session_interrupt`, `session_close`, `session_restore`, `session_trash`,
  `session_rename`, `session_cd`, `task_add`, `task_list`, `task_cancel`, `search`, `export`, `providers`,
  `session_wait` (until a session is done: its last answer only), `schedule_add` / `schedule_list` / `schedule_cancel`,
  `notify` (a desktop notification), `session_fanout` / `group_status` / `group_cancel` (below), and for
  the interface and itself: `ui_state`, `ui_focus` (show a sub-session while it goes on talking, `g` to come back),
  `ui_layout`, `ui_style`, `ui_panel`, `remote_control` (its own Remote Control), `settings_get` / `settings_set`
  (every option of the settings page), `cluster_info` (version, paths of its files, global session, agents and their
  commands, voice - speech model, models installed, what is missing -, service, interface: no search in its files),
  `config_files` / `config_read` / `config_write` (its own system prompt - it is
  started again on it after its turn -, the one of the sub-sessions, the vocabulary and the words of the voice,
  config.toml checked as TOML before it is written; the map of this computer read only), `machine_sync` (the question
  "Map this computer?" shown in the interface, the user answers it), `session_set_model`, `usage`, `session_display` / `session_display_update` / `session_display_get` (a rich display in a transcript,
  below), `external_conversations` / `session_import` (the
  conversations of the other agents of this computer, opened here), `session_transcript` (whole entries of a transcript),
  `session_context` (a context given to a session: another session, a conversation of an agent, a file),
  `session_messages` / `session_edit` (the real conversation of a sub-session of Claude Code rewritten: texts replaced,
  messages deleted, its end cut) and `session_fork` - these two only when the user allowed them (`[sessions] global_edit`,
  `global_fork`, off by default), `web_access` (the web access:
  address, code, on / off, kick), `voice_engines` (the
  engines of the voice, local and free-tier APIs: languages, strengths, limits, free use, links, ready, used),
  allowed without asking (`--allowedTools mcp__claude-cluster`);
- **questions of the agents** (AskUserQuestion of Claude Code, asked even in `bypassPermissions`): a popup on the
  session shown, like Claude Code / Claude Desktop - the terminal: one question at a time, its options and their
  description, ↑↓ move the cursor only (it is never an answer), 1-9 pick; one choice: Enter validates the option under the cursor and goes on; several choices: Enter / Space tick and untick (the answer follows the ticks, Enter never goes on); ← / Shift+Tab the question before, → / Tab the next one (answered or not, like Claude Code: going to and fro never changes a validated answer - it shows again with its option marked ✔, only Enter on another option changes it - and the review flags the ones left; on the only question → / Tab sends it once answered), Other typed, Esc declines; the window / the web page: the same (a click on a radio validates it, check boxes tick, Enter ticks a box, Next only goes on); the voice: a bare "next" needs an option chosen first - Esc declines; the window: a dialog
  (radio buttons or check boxes, Other, Answer / Decline); its notice and notification tell the question; the global
  session sees them in `session_status` and answers with `session_allow` `answers` {question: label}; a plain allow
  is refused (the agent would go on without its answer). One question at a time for the whole cluster, shared by the
  keys, the mouse, the voice and the web page: the question of a sub-session is shown on the global session
  (`[sessions] questions_to_global`, on), its own view greyed (*waits for your answer: Ctrl+G*); the voice answers it
  (read aloud with its options when `speak` is on): a number or the label of an option chooses it, a word of `[send]` /
  `[next]` validates it (the next question; the last one: all sent), `[back]` the previous one, `[other] <answer>`
  types it, `[cancel]` declines (`voice-words.txt`). **The global session answers** the whole set for you: the key of the
  global session (Ctrl+G) in the terminal, *Global answers* in the window, the web page and the notification, or a word
  of `[global]` said (*la globale*, *laisse la globale répondre*, *let the global answer*): it chooses from the
  conversation, the project and `machine.md`, answers with `session_allow`, then tells you what it answered.
  **Review** (several questions, like Claude Code): after the last one, every answer on one page - *Submit* (Enter, 1)
  sends them, *Cancel* (Esc, 2) declines, ← goes back to edit the last one (the window: Answer opens the review, Back
  returns to the questions; the voice: *valide* submits).
  **Chat about this** (Ctrl+T in the terminal, a button in the window, a field in the web page): a chat about the
  questions inside the popup, with the model of the session (the questions and its last messages as context, a
  one-shot run per message): the conversation of the agent is never touched (no fork, no resume), the question stays
  open; its chat is shared by the interfaces and goes with the question once answered. In the terminal it has its own frame
  (*chat about this*), wrapped, within a height that keeps the popup inside the screen: the newest lines at the bottom,
  the older ones scrolled with PgUp / PgDn, Ctrl+↑ / ↓ or the wheel over it (`▲ n line(s) above`, `▼ n newer`). `[sessions] global_answers` (off): the global session is told those
  questions and may choose their answer when it knows what you want;
- **the safety check of Claude Code** (a removal it cannot resolve, `rm -f $O/*.png`...): only a person may approve it.
  A sub-session in `bypassPermissions` asks for it: the global session decides (`[sessions] bypass_to_global`, on; it
  asks you when unsure), you can answer it too. In `auto` mode Claude Code denies it at once without asking: it is then
  shown to you as *safety check* (its reason under it); allowed, the session leaves `auto` for that turn, runs the same
  command again (allowed at once) and goes back to `auto`. The reason of every permission is shown with it;
- **the classifier of the `auto` mode giving no verdict** (a failure on its side, not a refusal): one short line counted
  (×N) instead of its long message each time; two in a row, the session goes to manual mode for the rest of the turn
  (its tools asked to you instead of failing again), then back to `auto`;
- autonomy (from its prompt): what the user asks explicitly is done without asking again; what it decides alone is
  proposed first;
- **Remote Control** (`remote on` / palette): the global session itself on claude.ai and the Claude app (the
  `remote_control` request of Claude Code on its own process): the same claude for both sides, live both ways - what
  is said on claude.ai appears here as it happens, a prompt typed here doesn't stop anything. Its link is shown in the
  header of the global session; it is on again at every start (and after `/clear`, `/model`, a rewind) until
  `remote off`. A background session of the old Remote Control (`claude --bg`) still holding the conversation is
  stopped at start (its conversation kept) and Remote Control goes on in the session itself. A prompt sent from
  claude.ai shows here like a typed one (and goes to the history): claude replays every prompt it gets
  (`--replay-user-messages`), the ones written here carry their own uuid and are not shown twice.

### The MCP page of the settings

`F9 > MCP` (the window: its MCP tab): every tool of the global session with what it does, each one on or off
(`[mcp_tools] <tool> = false`: refused at once with a message for the user, left out of its tool list at its next

### The icon and the notifications

The settings have a **Notifications** page: all of them on / off, *when* (`unfocused`, default: only when
claude-cluster is not in front, its own popups are; `always`), each kind on / off (the global session, a session
finished, a permission, a question, an error, the limits, the web devices, the task queue, the reminders, something
slow ready: claude-cluster started, the speech model loaded, the map of this computer written) and the sound.

The icon is a stack of terminals whose front one has a face made of prompt characters; the app is `^_^`, and the face
follows what claude-cluster does: the title of the terminal and its bar, the icon of the window, the tab of the web
page, the dock (the number of the sessions waiting on you, else running: the Unity launcher API), `claude-cluster icon
[face] [badge]` (its SVG, for a status bar). It changes at once everywhere (a turn ended, its happy moment over 20 s
later, an error, a question): the core tells every interface and the web page then, not at their next poll; an
interface adds its own voice listening. The binary installed writes its icon in the icon theme and
`claude-cluster.desktop` (the menu, the dock, the notifications grouped under it).

| Face | The app now | A notification |
|---|---|---|
| `^_^` happy | the global session just answered | the global session answered, a browser connected (web access) |
| `>‿<` grin | a session just finished | a session finished (its tokens), the task queue done |
| `•_•` attentive | a question or a permission waits, the voice listens | a question (its options as buttons), a permission (Allow / Deny), a reminder |
| `o_o` waiting | an error, the safety check of Claude Code | an error, a crash, the safety check (Run it anyway / Leave it), a limit close (80 %, 95 % of 5 h / 7 d) |
| `-_-` idle | nothing running | a limit reached (the usage, the budget): until its reset |
| `>_<` squint | something running | |

Never twice: the one who sent the last prompt of a session is notified for it - the desktop here (terminal, window,
voice, the global session) or the web device that sent it (its page, its app), even on this same computer; a device
asking to connect is always notified here. A notification clicked (its body or Open) shows its session: the window comes to the front, the terminal rings (its
tab or window marked: a terminal can't be given the focus on Wayland), the page and the app open the session. On a
phone: the page notifies through a service worker (Chrome on Android); the Android app gets every notification of the desktop
(next paragraph), its own watch service no longer guesses from the state. One notification per session (the next one replaces it), urgent when it waits on you, its buttons answered from the
notification (Open shows the session), a short sound of the desktop theme per kind (`[ui] notify_sound`).

**The Android app** gets the same notifications - the end of the global session's answers, a long task or a task queue
finished, a session waiting on a permission or a question, errors and limits, schedules / reminders, the `notify` tool
(and, off by default on a phone, claude-cluster ready and the web devices): the core logs each one (the last 100, kinds
and `[ui] notify_*` settings as on the desktop, whatever `[ui] notify` and `notify_when` say of the desktop) and the app
follows that log by a long poll, `GET /api/notify?since=N` (answered at once when there is a new one, else after 25 s;
no `since`: only the current number, nothing replayed). `[ui] notify_app = false` (*Settings › Notifications › Android
app*) publishes none. Each phone chooses for itself (*This device*, *Notifications of this phone*): on / off and which
kinds, *Send a test*, *Allow notifications* (the Android 13+ permission `POST_NOTIFICATIONS`, asked at the first start,
then the Android settings of the app) and *Keep running in the background* (battery optimization). They show while the
app is **not in front** (in front the page has its own center); Android channels per family (*Waiting for you*,
*Sessions*, *Errors and limits*, *Reminders and messages*: high; *Information*: low; each tuned in the Android settings),
grouped per session (one header per session), a tap opens that session. The logo of claude-cluster everywhere: a flat white status bar icon (the terminals, the face cut out; generated by `android/build.sh` from `claude-cluster icon` at every density), the coloured logo as the large icon, its blue as the accent - also on the foreground service notification. **No Google services**, so no push: the app keeps
its own connection to the computer with a foreground service (a quiet "following your sessions" notification, started
when the app leaves the front, again after a boot or an update of the app, reconnecting with a growing delay when the
computer is not reached, the ones of the last hour replayed after Android restarted it). What it cannot do: reach a
computer that is off or out of the network, survive an Android that kills the service despite the battery exemption (some
vendors do: allow the app to autostart in their settings), nor answer a permission from the notification (it opens the
session). An older computer without `/api/notify`: the app falls back to following the sessions this phone sent the last
prompt of.

### Model and thinking policy

The global session runs on `[global] model` / `effort` (until you change them) and sets the **model and the thinking of
the sub-sessions** itself (`session_set_model`, `session_spawn`, `/model` and `/effort` sent to a session; the tool
`models_policy` gives it your rules). **Settings > Model policy** (`[policy]`, protected: it never changes them):

| Setting | What it does |
|---|---|
| Default model / thinking | what the sub-sessions start from (empty: none) |
| *How the default applies* | `free`: none, by the task · `advise`: the start, deviate for a reason · `force`: nothing else, anything else refused with the reason |
| Allowed models / thinking | the only ones it may choose (a name or a part: `haiku, sonnet`) |
| Ask before a costly choice | the **costly** models (`opus`, `fable`: by name or part) and efforts (`xhigh`, `max`, and above): a question on every interface (Allow / Deny, a notification) |

Its system prompt always carries a **routing guide** (from the binary, `templates/routing.md`): cheap model and low
thinking for lookups and mechanical work, balanced for ordinary coding, premium and high thinking only for hard problems;
start low and escalate on a real failure; never move a large session to a stronger model for one step (its whole context
is re-read at the new price) but open a new sub-session with a short brief, so no context is duplicated, one per sub-task
that needs another model. The tool `models_policy` gives it your rules live: the models of its provider with their tier,
price, whether they are costly / allowed and **what a turn of each really cost you**, the efforts ordered by cost, and the
spending against your limits.

A costly choice returns at once to the global session (`asked`): the session keeps its model (a new sub-session starts
on the default) until you answer; Allow applies it (the conversation goes on) and tells the global session, Deny keeps it
and tells it why. These questions are yours alone: the global session cannot answer them (`session_allow`, the ask
commands). A change you make yourself (palette, `/model`, `claude-cluster model`) is never gated.

### Statistics

`F10`, `/stats` or the palette (*Statistics*) opens the **Stats** session, built by the core from the usage ledger (`usage.jsonl`)
and the activity log (`stats.jsonl` in the data folder): display blocks refreshed in place every minute while the session exists
(nothing is ever sent to an agent). It shows the cost and tokens today / 7 days / this month, the cost and tokens per day (30 days),
the cost by model and by provider (`api` key, `auth` login or `local`), the sessions that cost the most (turns, tokens, cost, cost per
turn, working time), the cache read / written and thinking shares, the time (core uptime, availability since the first start, agents
working, average and longest turn), the heatmap of the turns (weekday x hour, 90 days), the tools used with the permissions
allowed / always / denied, and the limits reached and errors. The activity events (start, a sign of life each minute, stop, tool,
permission decision, limit, error) are recorded in `stats.jsonl` from this version on; the older turns only have the usage part.

## Voice

`[voice] enabled = true`, then one of three listening modes:

| Mode | Listening | Prompt |
|---|---|---|
| `push` | push-to-talk key (F5: start, F5 again: stop; a sentence ending just after is kept) | every sentence heard while listening |
| `auto` | always, from the start (no key; F5 pauses / resumes) | every sentence heard |
| `wake` | always | only after the wake phrase (`wake_word = "ok claude"`, variants separated by commas): "ok claude, list the sessions" sends it; "ok claude" alone arms the listening `wake_seconds` (optional spoken `wake_reply`) and the next sentence is the prompt |

- The speech model is loaded at the start (about 10 s, `… loading the speech model` in the status line), in every
  mode: F5 listens at once.
- The sentences of one utterance are one prompt (push mode: everything said until F5 closes; auto / wake modes: the
  sentences heard before the confirmation ends). `<session>: ...` goes to that session only for its exact id / name.
- `only_me = true`: only the enrolled voice of the user (`voice-enroll`).
- The prompts of the voice reach the global session marked `[voice]` (its system prompt asks again when a word looks
  misheard); the mark is not shown in the transcript nor kept in the history.
- What is heard shows live in the voice bar (🎙, in italic), then the sentence waits `confirm_seconds` with its target
  and its countdown, and its buttons **✓ Send now / ✗ Drop / ✎ Correct** (the terminal and the window, every interface
  of the core); also Enter on an empty prompt (send), Escape (drop the last one), Ctrl+C (drop them all), the palette,
  or the send / cancel words said alone. The global session gets it as `[voice] ...` and asks when a word looks wrong
  or the request is ambiguous.
- `session <name> <text>` (or `<name>: <text>`) goes straight to that session.
- **Speech model** (`[voice] listen_model`, settings page > Voice; empty: the choice of `voice-models use`):
  `parakeet` (NVIDIA Parakeet TDT 0.6B v3, int8, 640 MB: French, English and both mixed, the text live while speaking -
  the piece being said decoded again every second or so -, the sentence final ~1 s after its end), `whisper` (Whisper
  small int8, 360 MB: slower, 3-6 s, its live text every 3 s or more), `kroko-fr` (the
  French streaming model: live text, the fastest, French only), or the free-tier APIs `groq` / `deepgram` (below).
  `voice-models list | use <m> | install <m>`; changed in the settings, voice-listen starts again on it.
- **Engines** (free or free-tier only; the settings page > Voice shows, for the value chosen with ←→, what it handles,
  its strengths and limits against the others, its free use, its voices and its links; `claude-cluster engines`, MCP
  tool `voice_engines`):

  | Engine | Kind | Where | Languages | Strengths | Limits | Free |
  |---|---|---|---|---|---|---|
  | `parakeet` | speech to text | local | 25 European | best local accuracy, French / English mixed, live text | ~1 s after a sentence, 640 MB | unlimited |
  | `whisper` | speech to text | local | 99 | widest coverage offline | 3-6 s a sentence | unlimited |
  | `kroko-fr` | speech to text | local | French | streaming, fastest, 68 MB | French only | unlimited |
  | `groq` | speech to text | API | 99 | Whisper large-v3-turbo: best accuracy, ~0.5 s | audio sent, no live text | 8 h of audio a day |
  | `deepgram` | speech to text | API | 40+, `multi` mixes 10 | language switched inside a sentence | audio sent, no live text | $200 of credit once |
  | `piper` | text to speech | local | ~40 | instant, light; the fallback of the others | synthetic voices | unlimited |
  | `kokoro` | text to speech | local | 8 (fr: 1 voice) | natural, read sentence by sentence | ~1 s a sentence on CPU, ~600 MB loaded | unlimited |
  | `elevenlabs` | text to speech | API | 32 | very natural, largest voice library | text sent, small quota, non-commercial | ~20k characters a month |
  | `cartesia` | text to speech | API | 42 | fastest (~0.2 s), speed / emotion controls | text sent, credits once, non-commercial | 20k characters once |

  `[voice] listen_model` picks the speech to text, `listen_language` the language spoken (whisper and the APIs; empty:
  found by the model), `say_engine` the text to speech and `say_voices` its voice per language (`fr=ff_siwis,
  en=bf_emma`; `es=kokoro:ef_dora` another engine for a language; missing: the engine's default for it). The language
  of an answer is found from its words (French, English, Spanish, Italian, German, Portuguese, Dutch). The APIs: their
  key by `claude-cluster auth login <groq|deepgram|elevenlabs|cartesia>` (read by voice-listen / voice-tts from the
  keyring or credentials.json, never on a command line, or `$GROQ_API_KEY`...); a failing API (no key, network, quota):
  the sentence recognized by the local model, the answer read by Piper (`voice_fr` / `voice_en`). Kokoro:
  `voice-models install kokoro`; its server (`voice-tts --serve`) keeps the model loaded and ends after 15 min unused.
- **Sentences** (parakeet / whisper): from 0.6 s before the speech is detected (its soft first syllable kept) to
  `[voice] end_silence` of silence after the last voice (default 1.0 s: a short pause, two sentences said in a row are
  one sentence; the cut just after the last voice, never in a word), recognized piece by piece between its pauses (each
  piece its own language: French and English mixed), a speech longer than 30 s cut at a pause. While the user speaks
  ("…", and 2 s after for the end of the sentence) the countdown of a transcription waiting is paused ("paused while you
  speak"), then full again once the new text is added - or sent / dropped at once by a send / cancel word.
- **Said alone while a transcription waits** (compared without case, accent nor punctuation, no wake phrase needed):
  a cancel word ("annule", "stop", "laisse tomber", "cancel"...) drops it, a send word ("envoie", "valide", "vas-y",
  "go", "send"...) sends it at once; nothing waiting, a cancel word stops the answer being read and the turn of the
  global session (only heard while it speaks with `voice-listen --duplex`). The words: `voice-words.txt` of the config
  folder, edited in the editor (settings page > Voice > *Voice words (edit)*, palette *Voice words*), one per line under
  `[cancel]` / `[send]` (`[voice] cancel_words` / `send_words` add more).
- Ctrl+C or Esc stop the reading (an answer read after its turn too, the turn interrupted when it runs); the reading
  stops with claude-cluster (voice-say and its piper | pacat in a group of their own).
- **Vocabulary**: the proper names the recognition bends are written back in every sentence heard, before it is shown,
  routed and sent: the file `vocabulary.txt` of the config folder (`[voice] vocabulary`; settings page > Voice >
  *Vocabulary (edit)*, palette *Vocabulary of the voice*), one name per line with the ways it is heard
  (`libutils = lib utils, lib you tils`), plus by themselves the names of the sessions, the projects of the map of this
  computer and your names (`[user] nickname`, the login). A long name (7+ letters) is also found one or two letters off;
  a common word is never replaced.
- Answers of the global session are spoken as a short summary, in their language (`say_engine`, `say_voices`; Piper:
  `voice_fr`, `voice_en`); F6 stops.
- The palette action **Voice: what is missing** lists what to set up (tools, enrollment, voices, English speech model,
  the model or the API key of the engines chosen).

## Updates

A newer claude-cluster installed over the running one (`setup.sh`, a package: the binary on disk replaced, its version
higher; a rebuild of the same version or an older one: nothing) is seen by the core within seconds and offered in
every terminal and window: **Update** (the default: Enter / `u`), **Ignore** this version (offered again for a newer
one), **Quit** (everything stopped, to start again by hand), Esc later (the palette: *Update claude-cluster*). Update:
a progress popup - the turns running end first (their sessions named), the sessions saved, then the core runs the new
binary in its own place (same pid: a systemd service keeps running, same arguments, the sessions resumed at once), its
terminals and windows follow it by themselves (an *Updating claude-cluster…* popup while it starts, then each one runs
the new binary too, same pid, same terminal) and the web pages reload; the conversations go on (`--resume`), a notice
says `updated: 1.4.17 -> 1.4.18`. Never from the web page or the global session (the user only).

## Plugins and skills

Like the plugins of claude.ai: **sources** of plugins / skills (settings > Plugins > Sources, `[plugins] repos`) - a
git repository (GitHub `owner/repo`, an https or git URL), a folder of this computer, or a `.zip` - listed by the
core: a repository cloned (shallow, pulled at each start of the core), a `.zip` unpacked (again when it changes), a
folder read in place, in `<data>/plugins` (its index `index.json`). A Claude Code marketplace
(`.claude-plugin/marketplace.json`) offers its plugins, else the folders with a `SKILL.md` are skills.

What is ticked is installed by the core, for the sessions started after it: a plugin by `claude plugin marketplace
add` + `claude plugin install <name>@<marketplace>`, a skill by a link in `~/.claude/skills`; *All of a source* takes
every item (the new ones too); turned **off** (`[plugins.off]`): a plugin disabled, a skill unlinked, both still
installed; unticked: removed - only what claude-cluster installed (a skill or plugin of the user of the same name is
never replaced: told). These settings are protected (never changed by the global session, a confirmation for the
sources: their code runs as you).

The **browser** of the terminal (`/plugins`, the palette *Plugins*): the sources and their items (● on, ◐ off, ○ not
installed), `i` install, `r` remove, Space toggle, `e` on / off, `a` add a source (a path completed by Tab, a link; a
file or a folder **dropped** on the terminal is added from its path), `d` drop a source, `u` update; Enter / →: the
information of the item and the **tree of its files** (▸ / ▾ folders, like nvim-tree), a file previewed with its
colours (its language; Markdown drawn: front matter, headings, bullets, code blocks), PageUp / PageDown; the mouse
too. The window and the web page have the same sources and ticks in their settings.

## Conversations of the other agents

The conversations of the agents of this computer opened outside claude-cluster (Claude Code: `~/.claude/projects`,
Codex: `~/.codex/sessions`, Qwen Code: `~/.qwen/projects`, opencode: `opencode session list`) are offered in the palette
(*Open a conversation of Claude Code: ...*), the web page (*Open a conversation of another agent*), `claude-cluster
external` and to the global session (MCP `external_conversations`). Opened, one becomes a session resuming it in its
folder: its transcript so far shown (the active branch of Claude Code), the same conversation goes on here. A
conversation of Claude Code used less than 2 minutes ago (maybe still open in a terminal) is opened as a copy
(`--fork-session`): the original stays untouched. The ones opened here are not offered again.

- **Fork** (palette *Fork the session*, the web page, `claude-cluster fork <s>`): a copy of a session of Claude Code, its
  conversation so far, then each one goes its own way. The global session may do it only when allowed (settings page >
  Sessions > *Global session can fork*, off by default): to give a new sub-session the context of another one.
- **A context** (MCP `session_context`): the conversation of another session, of an agent, or a file, given to a session
  as a prompt it keeps for its next requests.
- **Edit** (MCP `session_messages` / `session_edit`, only when allowed: *Global session can edit*, off by default): the
  real conversation of an idle sub-session of Claude Code (what its model sees) rewritten - texts replaced, messages
  deleted (a tool call and its result together), its end cut; written as a new conversation next to the old one (kept),
  the session started again on it and its transcript shown again.

  and `banned.json` (0600); the trusted and banned ones are listed and edited while the web access is closed too (the palette *Web
  devices*, `claude-cluster web`). `claude-cluster web ban <ids>` / `web unban [ids|all]` too.
- **This network only**: the browser must have a private address (10/8, 172.16/12, 192.168/16, 169.254/16) of the
  subnet of one of the interfaces of this computer (or be on this computer); the page answers only by the address or
  the name of this computer (a public name pointed at the LAN refused) and the requests of another site are refused.
- From the page: the commands of the sessions (list, read, send, allow, interrupt, spawn, close, rename, mode, model,
  tasks, trash, restore...) and the settings (its settings page); never the web access itself (its devices, its
  trust: here only).
- **HTTPS** (`[web] https`, on by default; built with OpenSSL): an authority of this computer made once in
  `~/.config/claude-cluster/web/` (`ca.pem`, its key 0600), and the certificate of the server signed by it, naming every
  address of this computer (made again when they change, and 30 days before its end). **No browser warning** once the
  authority is trusted by a device: this computer with `claude-cluster web trust-ca` (the palette: *Web access: trust
  its certificate*; the system store, read by Firefox, Chrome and curl; `web untrust-ca` undoes it), the other ones
  from the login page (*trust this computer once*: `/ca.crt` and the steps for Android, iPhone, Firefox, Windows,
  macOS). The code and the conversation are encrypted, and the microphone of the page is allowed (browsers refuse it
  on plain http). A plain `http://` request is sent to `https://`. Off: plain HTTP, no microphone.
- **The certificate fitting the way it is reached**: with *Beyond the LAN* = `tailscale`, claude-cluster gets the
  **real certificate of the tailnet** (`tailscale cert <computer>.<tailnet>.ts.net`, Let's Encrypt) and serves it to
  that name (SNI): **no warning on any device, nothing to install**; got apart (its own popup: Let's Encrypt takes
  seconds, a minute; the authority of this computer serves meanwhile), renewed every day without closing the port. The
  LAN address and the router keep the authority of this computer (trusted once per device: no warning, and nobody else
  can make a certificate it accepts - its key never leaves this computer). Needed once: the HTTPS certificates of the
  tailnet on (login.tailscale.com › DNS › HTTPS Certificates) and this user allowed to ask for them (*Services ›
  Outside › Allow tailscale certificates*: `tailscale set --operator=$USER` by the password window). Missing: told in
  red in the settings, its failure popup (Retry), the authority served meanwhile. Note: a public certificate is listed
  in the public Certificate Transparency logs - the name of the computer in its tailnet is public, nothing else
  (reaching it still needs the tailnet). *Services › Web access* tells the certificate served and its fingerprint.
- A firewall may have to let the port in (`[web] port`, 8787: `firewall-cmd --add-port=8787/tcp`; the Fedora
  Workstation zone already lets 1025-65535 in).

### Terminal mode

The terminal interface of claude-cluster itself (`claude-cluster --tty`: its panels, its keys, its mouse, its popups)
can run in the browser and in the window, as if you sat at the terminal of the computer.

- **In the browser**: the web access serves a *terminal page* on its own port, `[web] tty_port` (2222 by default; 0:
  off; outside: `tty_remote_port`, 0: the same port), with the same code and approval as the page; the ⌨ button of the
  page opens it. A real `claude-cluster --tty` runs in a pty on the computer for each connected device (kept while the
  page reads it, closed 2 minutes after the page is gone, 8 at once at most). One encrypted WebSocket (`wss://`, the
  same port and cookie) carries every key and the screen: the computer keeps the screen (its own terminal emulator) and
  sends only the rows changed, at once when the terminal ends a frame (about 10x fewer bytes than its raw output, a key
  echoed in about one network round trip instead of several), the page draws only those rows; its bar shows `live ·
  ping … ms · … fps`. Without a WebSocket (a plain http build, a proxy that drops it) it falls back to polling. The
  socket is checked like the page: the device connected (its cookie, its address; kicked, logged out or banned: closed
  at once), the Origin of this page only (no other site may open it), never the app, masked frames of 1 MB at most, 4
  per device, closed after 30 s of silence. **⛶ fullscreen** locks the
  keyboard (Chrome / Edge): Ctrl+T, Ctrl+N, Ctrl+W... reach the terminal instead of the browser (F11 or Esc held
  leaves); elsewhere use the Alt doubles (Alt+N, Alt+P). The rules of the page apply inside it: the shell (`!`) only
  with *Shell from the page*, the settings sections of *Settings from the page* only, the services with `services`, no
  key (`/login`), nothing installed; the app never gets it (a browser only: its own page is for the phone).
- **In the window**: `claude-cluster -g --tty-mode` (or `[ui] gui_mode = tty` to keep it) shows the terminal interface
  inside the window (a pty of this computer, the window stays the core of the sessions): every key of a terminal,
  the mouse, resized with it; the terminal quit (Ctrl+Q) closes the window.

## Security

What protects the three ways of using claude-cluster, and what stays your responsibility.

- **Local** (the terminal, the window, the CLI, the MCP): everything goes through a unix socket of your runtime folder
  (`0700`, the socket `0600`): only your user (and root) reaches it. Any program running as you - a script, an agent
  in `bypassPermissions` - may drive claude-cluster through it (read the transcripts, send prompts, allow a tool): the
  same trust as your account. The API keys live in the keyring (`secret-tool`) or `credentials.json` (`0600`), given
  to the agents by their environment only, never in `config.toml`, the logs or the transcripts (an agent printing its
  key in an error would show it in its transcript); an agent gets them on a pipe, never on its command line
  (`/proc/<pid>/cmdline` is readable by every user of the computer). The config and data folders
  (`~/.config/claude-cluster`, `~/.local/share/claude-cluster`: the conversations, the prompt history, the keys of the
  web access) are `0700`. The programs run with your rights (`commands.*`, the editor, the image viewer, the
  terminal / python of the service, the voice commands) are confirmed before they change.
- **Web access on the LAN**: https on by default (the authority of this computer, its key `0600`; TLS 1.2+), a plain
  request sent to https. A device gets in with the 6-digit code **and** your approval (`[web] approve`, on by
  default); a trusted device (its 32-byte secret, `trusted.json` `0600`) comes back by itself. The session cookie
  (24 random bytes, `HttpOnly`, `SameSite=Strict`, `Secure`) is bound to the address of the device. 5 wrong codes:
  the address blocked 15 min and a new code. Only the private addresses of the subnets of this computer are served;
  the `Host` is checked (no DNS rebinding), a `POST` needs the right `Origin` (no CSRF), the page has a CSP,
  `X-Frame-Options: DENY`, `nosniff`, HSTS; TLS without renegotiation. 64 requests at once at most (the rest told
  busy). The page escapes everything it shows (the transcripts as text, the markdown of the displays escaped whole),
  and its script is the only one allowed (a CSP nonce of each response: an injected script never runs). The code and
  the secrets are compared in constant time; the names of the files downloaded are cleaned (no header injected).
  `install_package` installs the packages a setting needs only (the password window names `dnf`, not the package).
  A body bigger than 4 KB is read for a connected device only; 8 connections at once per address. A request of the
  control socket never stops the core (anything it throws is answered). A key typed in the palette is never shown
  (no popup, no notice).
- **The global session runs in `bypassPermissions`** by default (`global.permission_mode`: *never asked*): what reaches
  it (your prompts, the replies of the sub-sessions, a context) is obeyed with your rights, commands included. That
  is the point of an orchestrator, and its risk: a prompt injected in a sub-session (a web page it read) comes back
  to it as a reply. `auto` there makes it ask you before a command (the MCP tools of claude-cluster stay bounded
  anyway).
- **Web access from outside**: https required (a plain peer from outside is refused before any handshake);
  `tailscale`: only the addresses of your tailnet, the real certificate of the tailnet when it is on; `router`: the
  login page is reachable by anyone on the Internet - the code **and** your approval are needed, 5 wrong codes block
  the address 15 min and rotate the code. The code, the conversation and the cookies are encrypted end to end; the
  key of the certificate never leaves this computer. `/ca.crt`, `/app.apk` and `/api/version` are served to anyone
  (nothing secret in them).
- **What an approved device can do**: everything you can from the keyboard, except a shell (`!command`, `:r !`)
  unless *Shell from the page* is on, and except the settings of claude-cluster: read only from the page unless
  `[web] settings` names the sections it may change (`all`, or `ui, notify, services...`; `services`: the actions of
  the Services tab; *Settings from the page* itself never from the page). *This device* stays the page's own. A trusted phone lost or unlocked = your claude-cluster: *Web devices* › trust
  no more / ban, and keep the shell off unless you need it.
- **The user's own controls stay the user's**: the voice keys (listen, send / drop / correct a voice prompt, mute) and
  the palette actions (log in / out, quit everything, start over...) are run by the core for its terminals and windows
  only - never by the global session (its tools) nor by the web page. The token of Claude Code (`~/.claude/.credentials.json`)
  is read for the usage endpoint of claude.ai only, sent by a header file readable by you alone from its first byte,
  removed at once, never logged; its endpoint is never taken from the config (a test one: the environment of the
  core). The folders of the transcripts (`[usage] transcripts`) are read under your home folder only, and only the
  `usage` numbers of their lines.
- **The global session and its MCP tools** run without a permission prompt (`--allowedTools mcp__claude-cluster`):
  what it may do is bounded. The **protected settings** - a shell or the web opened wider (`web.shell`, `web.remote`,
  `web.approve`, `web.https`, `web.enabled`, `web.port`), the permissions of the agents (`agent.permission_mode`,
  `agent.allow_bypass`, `global.permission_mode`, `sessions.bypass_to_global`, `global.answers / fork / edit`, `sessions.rewrite_global_prompt / rewrite_sessions_prompt`), the
  programs run as you (`commands.*`, `ui.editor`, `ui.image_viewer`, `service.*`, `voice.*_command`), the MCP servers
  and tools - are **never changed by it** (`settings_set`, `config_write` refuse them: it asks you, you change them
  in the settings page). The other dangerous changes ask you (`confirmed`). `[mcp_tools]` turns any of its tools off.
  It never writes a file but a `.md` / `.txt` out of the hidden folders (`export`: no `~/.bashrc`, no
  `~/.ssh/authorized_keys`), never gives a hidden file (`~/.ssh`, `~/.config`, `~/.aws`, the folders of
  claude-cluster) to a session as a context nor to the page as a download, and rewrites the system prompts (what every
  session obeys at its start) only when *Global session can rewrite its own system prompt* (`rewrite_global_prompt`, off by default: a
  prompt injected once could stay for good) and *... the system prompt of the sub-sessions* (`rewrite_sessions_prompt`, on by
  default) allow it, one per file - it gives you the text instead. The old `global_prompts` key still sets the first one.
  A sub-session in `bypassPermissions` with *bypass to global* on lets the global session decide its commands: an
  injected prompt (a web page read by a session) may then run commands through it - keep `agent.allow_bypass` off
  when you do not orchestrate.
- **The programs run for an answer** (`capture`: the shell asked for its aliases, upnpc, tailscale, git...) get no
  controlling terminal (`setsid`): an interactive shell could take the terminal of the interface and kill its keyboard.
- **Privacy**: the map of this computer (`machine.md`: hosts, repositories, the names of environment variables, the
  packages) is read by the global session, so sent to its API provider; the prompt history (`history.jsonl`) keeps
  what you typed, in clear, in your data folder.
- **The Android app**: it pins the authority of the computer the first time (its fingerprint shown, compared with the
  one of claude-cluster); its own requests trust the authorities of the system (a real certificate) or that authority
  - never anything else; its updates come from the computer and keep the signing key of the app.

## Background service

`claude-cluster service enable` installs and starts a systemd user unit (`~/.config/systemd/user/claude-cluster.service`,
started with the graphical session): saying the wake phrase (`[service] wake_word`, else `[voice] wake_word`: "ok
claude") opens claude-cluster with its voice on at once (`--voice auto`, `[service] voice_mode`): `[service] frontend =
"auto"` (default) opens its window when it can (built with Qt6, a display), else - or when the window fails to start -
a terminal (the first installed or `[service] terminal`); `"gui"` the window then a terminal on its failure; `"tty"` a
terminal only. Every try and its failure is in the journal (`service logs`); all of them failed: `FAILED to open`.
(The terminal that has the focus can't be used: GNOME on Wayland tells no one which window it is.)

| Command | Effect |
|---|---|
| `service setup [--debug]` | write the unit and the detector (`~/.local/share/claude-cluster/wake.py`); `--debug`: the unit runs `service run --debug` (setup again without it to stop) |
| `service enable [--debug]` / `disable` | set up and start now (a running one restarted on the new unit) and at every session / stop and not at the next one |
| `service start` / `stop` / `restart` | now only |
| `service status` | installed, active, enabled, DEBUG when it is, an instance running |
| `service logs [--follow]` | its journal (`journalctl --user -u claude-cluster.service`): start, detector, launches and their failures |
| `service remove` | stop, delete the unit and the detector |
| `service run [--verbose] [--debug]` | the loop the unit runs (`--verbose`: the end of the text of every sound; `--debug`: the whole text heard, the levels and the wake events - for the tests only) |

The journal always tells what the service does: its start (wake phrase, front-end, voice), the detector started /
ended by itself (its exit code) and the next try, the detector paused while an instance runs, every wake with the
exact command run, then `claude-cluster started (N ms)`, `failed at its start` with the last lines of its unit
(`claude-cluster-app-<time>-<n>.service`: `journalctl --user -u <unit>`) or `did not answer on its control socket
in 20 s`. Nothing heard is written there out of `--debug`.

- **Light**: the microphone is read all the time, but the speech recognition (the French model of `voice-listen`,
  one thread) only runs on the sounds louder than the background: ~2 % of one core in a quiet room (`voice-listen`
  itself: ~300 %), ~180 MB for the model kept loaded (so the phrase is caught at once).
- The agents run in a session of their own (`setsid`): the signals of the terminal (its tab closed) never reach them,
  claude-cluster stops them itself.
- **One claude-cluster**: while an instance runs (opened by the service or by hand) the detector is stopped (no
  microphone, no CPU); it starts again when the instance quits. The instance is started outside the unit
  (`systemd-run --user`): stopping the service doesn't close it.
- **Privacy**: nothing heard is kept longer than needed: the audio goes through one read buffer and a ring of 0.5 s,
  written over in place and zeroed; the recognition sees at most 3 s at a time; of its text only the last characters
  that can hold the phrase are compared (its length + 10); only the wake event leaves the detector, its buffer zeroed.
- `--voice auto|wake|push` also works by hand: the voice on for this run, whatever the config says.

## Configuration

**Settings page** (F9 or the palette: *Settings*), like a BIOS setup: one tab per section (Interface, Agent,
Commands, Global session, Sessions, Voice, Keys), the help of the selected option on the right, `*` on the changed
ones. Terminal: `↑↓` select, `←→` / `Enter` change a choice / toggle / number, `Enter` edit a text, `Tab` /
`Shift+Tab` section, **Ctrl+S** save (the page stays), **F10** save & exit (when the terminal lets it through),
**Esc** exit: with unsaved changes it asks "Save the changes? (y / n)", y saves, any other key drops them. Window: a
tabs dialog (help on hover, Ctrl+S save, F10 / Save save & close; closed with changes: asked). The changes are written in `config.toml` - only the values, its comments kept - and
reloaded live; the options marked *applied at the next start* need a restart. Profiles, providers and own styles
stay in the file.

**Dangerous values are confirmed at the save**: bypassPermissions (new sessions, the global session), `allow_bypass`,
`bypass_to_global`, `extra_args` skipping the permissions, the web access without approval, open to the Internet
(`remote = router`), its shell, plain http, an MCP server added. A yellow **⚠** next to each setting that can be
dangerous, its name **red** while its value is the dangerous one. Changing it asks nothing; the save (Ctrl+S, F10,
Save, Esc then save) shows one popup listing them with their warning: save them, or back (nothing saved, the changes
kept). The quit key (Ctrl+Q) in the settings closes the page without saving (not asked; claude-cluster goes on). `:set` needs `:set!`; the control and the MCP refuse it without `confirmed` (the global session asks you first). Each option shows its help under it (the window) or on the
right (the terminal), in lines and steps (Web > Beyond the LAN: how to set up Tailscale or the router).

**What a setting needs and is missing** is told in red on its right (the terminal: `✗ …`, its details in its help;
the window: under it; the web page: under it): a program not found (the editor, the image viewer, the terminal of
the service, the program of an agent), `upnpc` for `remote = router` - and when it is there, the router refusing to
open the port or its public address unknown, with what to do in the box -, `tailscale` missing or not connected. When
a package installs it: `[i]` / *Install …* installs it at once (the terminal: `sudo <dnf | apt-get | pacman | zypper>`
in the terminal; the window, the web page: the password window of the desktop, `pkexec`). The save lists the changed
settings missing something with the dangerous ones: install, then save / save anyway / back.

**A long operation** (an action of the palette, a local `/command`, a `!command`, `/clear`, the opening of the web
access and its router, a package installed, the previous run restored) runs without freezing the interface and,
past 0.4 s, shows a popup in every interface like the map of the computer: its title, a spinner and its time, its
step now (stopping the agent, starting it, asking the router...), its done steps and what it told greyed scrolling
under it, then its result (✓, or ✗ then its failure popup); Esc hides it in the terminal (it goes on). The popups come
one after the other: several operations at once wait their turn (one shown at a time, each with its result), a
failure popup after the progress one; they show while the operation runs (the interfaces redraw meanwhile, the web
access opened without blocking them).

**What failed of what you did** (an action, a command, a prompt not sent, the settings not saved, a turn ending in
an error, the port of the router not opened, an install) opens a popup in every interface: what you did, where it
failed (its source), the error, **OK** (Enter, the default) or **Retry** (`r`: run again; failing again, its popup
again). A request of the control socket (the CLI, a script, the MCP) is told by its answer only; the web page shows
the failures of its own requests the same way. The web line shows the public address only when it is reached for
sure (the router opened its port, tailscale connected, *Name from outside* given), else `outside ✕` and why.

**The Services tab** of the settings drives the sub services of claude-cluster, a card each (its state on the right
of its name, its details, its buttons; the terminal: ↑↓ a service, ←→ a button, Enter runs it, a click too; R reads
it again; the window, the web page: its buttons):
- **Service (systemd)**: the wake phrase while claude-cluster is closed (its detector hears it and opens a window or a
  terminal: what it opens is *Interface > Front-end*, the terminal *Interface > Terminal emulator*, its microphone

  Enable / Disable, Setup, Remove (asked first). Its detector is paused while claude-cluster runs (the microphone is
  the voice's of the core): what is heard now is under *Voice*.
- **Web access**: open or closed, its address and code, outside reached or why not; Open / Close now, New code, Ask

- **Core**: its pid, since when, its version / build, who started it (an interface, the systemd service, `serve`), the

## How it works

**Several terminals and windows at once** (`[ui] shared_core`, on): the sessions live in a core of their own
(`claude-cluster serve --linger`, started by the first terminal / window, its log in `<data>/core.log`); every terminal
and window is an interface of it, all in sync (the same sessions, prompts, questions, notices; sent again only when a
session changed). Its first interface asks the previous run; closing one leaves the others (the core goes on), the last
one closed stops it (the service, when it runs, is the core and stays). The core gone (a crash): started again by an
interface. Two prompts sent at once to one session from two interfaces: told on that session (a minute in its header)
and in the notices, the second one waits behind the first. Off: a second claude-cluster is refused, as before.

**Redraws** (terminal): an image is drawn when the state changed, 25 times a second while the prompt is typed or a text
is being revealed, 8 times a second while only a spinner or a popup turns (the spinners change every 120 ms: more images
were the same picture, ~2.5 times less CPU in a working session), once a second otherwise (the timers).

**Another version runs the core** (installed again while it runs, older or newer: its build is its version and the
date of its binary): a new terminal / window does not mix with it, it asks first (the terminal: a question, the
window: a dialog): **replace it** - the terminals / windows of the other version (the same install, the same socket)
and its core stopped (10 s, then killed), the sessions resumed by this version - or **quit**, nothing changed. An
interface of another build is refused by a core (told on it: close it and open it again). Only through the local
socket of this user, never the network; the service, its MCP servers and the headless commands are left alone (the
service: `claude-cluster service restart`).

```
claude-cluster core (one per user: control socket; serve --linger, or the service)
├── Manager ── Session g (global) ── claude -p --input-format stream-json ... --mcp-config mcp.json
│          ├── Session s1 ── claude -p stream-json (permissions: --permission-prompt-tool stdio)
│          ├── Session s2 ── qwen -p ... -o stream-json -r <id>       (one process per turn)
│          └── Session s3 ── opencode run --format json -s <id>        (one process per turn)
├── Control (unix socket) <── headless commands, claude-cluster mcp (MCP server of the global session)
├── Voice ── voice-listen --json / voice-say
└── interfaces: terminals (FTXUI) and windows (Qt6) of other processes (sync: their state; their actions run here), the web page
```

- The agents run through `env -C <folder> VAR=...` (provider environment), every pipe end of the cluster is
  close-on-exec: a session never keeps the pipes of another one.
- History: `~/.local/share/claude-cluster/logs/<id>.jsonl` (search, export, restore); `state.json` keeps the
  sessions (agent session id for `--resume`, cost, tokens), the trash, the tasks and the interface choices.
